== 1. The witness: three pieces

tools/nbd-recorder (host, Python stdlib). It is written from the NBD protocol
specification and nothing else:
- the fixed newstyle handshake;
- NBD_OPT_GO, NBD_OPT_INFO, NBD_OPT_EXPORT_NAME and NBD_OPT_ABORT; any other
  option answers NBD_REP_ERR_UNSUP;
- the transmission flags HAS_FLAGS, SEND_FLUSH and SEND_FUA; no TRIM, no
  WRITE_ZEROES, no structured replies, no multi-conn;
- READ, WRITE, FLUSH and DISC. A request out of range answers NBD_EINVAL.
It serves two exports from memory: `data` (a base image file, or zeros) and
`mark` (1 MiB). One lock orders every request on both connections. Each
request is logged as one line (seq, export, command, offset, length, FUA,
sha256 of the payload), with the payload bytes in an append-only blob file.
A FLUSH is answered only after every earlier write in the log is applied. An
armed rule answers one request NBD_EIO without applying it. The
unix socket lives under a short per-run VM directory and stays under 108 bytes.

tools/powercut-synth (shared by the host and the guest, Python stdlib, no I/O
but its arguments). It turns a log into crash states. For a cut at log
position c:
  durable(c)  = every write before c that a FLUSH before c covers, and every FUA
                write before c;
  volatile(c) = every other write before c;
  state(c, S) = zeros, then durable(c) and S ⊆ volatile(c), in log order. A
                write in S lands whole, or torn: only its first k 512-byte sectors.
Cuts are labelled by the marks (section 2). Window W(s) runs from the mark
before step s to step s's mark. Each window gives these states:
  before          state(mark_prev, ∅)
  after           state(mark_s, ∅)          only what the step made durable
  after-all       state(mark_s, volatile)   everything the step wrote
  flush-<j>       state(flush_j, ∅) and state(flush_j, volatile) for every
                  FLUSH inside the window
  subset-<k>      k = 0..3: seeded subsets of volatile(mark_s).
                  The seed is sha256(fs, verb, step, k). Each write is kept with
                  p=1/2, or torn at a seeded sector with p=1/4.
Identical images are deduplicated by digest, and their labels are kept.

tools/powercut-guest (runs as init's child in the guest). Phase run:
- mkfs the data disk (ext4 by default, or ext3);
- mount it data=ordered,noauto_da_alloc, so ext4's rename heuristic cannot hide
  a missing fsync;
- build the fixture repository on tmpfs;
- set up the scenario root on the data disk, as tools/check-transactions'
  scenarios do;
- sync, write the mark `setup <verb>`, and digest REF_OLD;
- run the historical test-only failpoint executable <verb> with <former-prefix>_FAILPOINT=mark, write the mark
  `end <verb>`, and digest REF_NEW;
- print both digests and the trace, then power off without unmounting (sysrq o).
Phase check:
- rebuild every planned state in tmpfs from the shipped log;
- loop-mount it (the kernel replays the journal) and read `lrd status`;
- run `lrd rescue` and digest R1; run it again and digest R2;
- unmount, mount again and digest R3;
- unmount, then require `e2fsck -fn` to be clean;
- print one line per state.
The host driver tools/check-powercut does three things:
- builds the guest binaries in px75-ubuntu:2 from the same commit, with their digests printed;
- makes the payload disk, a raw tar;
- boots QEMU (-enable-kvm, 2 vCPUs, 2 GiB), with vda the rootfs (read-only),
  vdb the payload (read-only), and vdc/vdd the recorder's data and mark exports.
It then plans the states, runs the check boot, and prints the rows.

== 2. The one the package manager change: the mark action

the historical test-only failpoint executable accepts <former-prefix>_FAILPOINT=mark with <former-prefix>_FAILPOINT_MARK=PATH.
At every hook it writes one 512-byte record "MARK <point> <detail>" at offset 0
of PATH, fsyncs it, and prints "MARK <point>" on stderr, as trace does. On the
mark export the recorder logs each record in order with the data writes. A
hook runs after its step's durable action, so the mark for step s arrives after
every flush s waited for. The shipped the package manager still reads no failpoint input. A
block device rejects O_APPEND writes, which is why the record always goes at
offset 0. The predicted hook order for a two-file upgrade:
lock capacity stage backup:0 backup:1 intent-written intent apply:0:walk
apply:0:temp apply:0:renamed apply:0 … generation commit-written commit-renamed
commit cleanup:backup cleanup:stage cleanup:intent cleanup:dir done.
Rescue adds rescue:undo:<i>, rescue:relink:<i>, rescue:generation and
rescue:cleanup:*.

== 3. The pass condition (pm00's, made exact for a power cut)

For every planned state of (fs, verb), all of these must hold:
- the image mounts; a journal replay is allowed;
- `status` reads recovery-needed exactly when a transaction directory is visible;
- both rescues exit 0, and the second says "rescue: nothing to do";
- R1 == R2 == R3;
- R1 is in {REF_OLD, REF_NEW}, and by position:
  - R1 == REF_OLD for every state in a window up to and including W(commit-written);
  - R1 is either in W(commit-renamed) and W(commit), excluding the after state of
    commit;
  - R1 == REF_NEW for commit's after state and every later state;
- `verify` passes;
- no t<N> or .<former-name>-t<N>-* name remains;
- `e2fsck -fn` exits 0.
The digest is pm04a's (docs/TRANSACTIONS.md X10) with owners applied, because the
guest runs as root. "Recovered twice identically" covers two things:
- R1 == R2 (rescue is idempotent);
- R3 == R1 (the recovered tree survives a remount).
A rescue refusal on any planned state is a FAIL: every power-cut state must be
recoverable.
