Toolchain bump prediction (2026-11-20)

Baseline: trunk 032e97b6. Pins today: wolf 0.2.38, lupin 0.1.60, std 23baa1a.
Target: wolf 0.2.40, lupin 0.1.62, and std at the commit wolf 0.2.40 bundles
(be1d10fa), which is 56 commits past d4a4d4c, the public-PKI TLS client.

The old std already has std.x.tls.client, but not std.x.crypto.p384 or
std.x.crypto.rsa, and its client offers no P-384 or RSA-PSS scheme. A row that
builds a probe importing those modules and checks the scheme numbers, the
six-scheme offer and the P-384 self test should therefore fail to build at the
old pins (unresolved module) and pass at the new pins.

Prediction for the bump: the sources build unchanged under wolf 0.2.40 and
std be1d10fa; no source edit is needed; every existing row passes with the same
output. The one thing that might break is a std API the code uses that moved
between 23baa1a and be1d10fa (sha2, json, hex, str, curve25519 for the trust
code). If something does, the fix is a pin matter only when it is a rename; a
behaviour change is reported, not absorbed. The row itself might also need the
net capability declared for the TLS client import; if so that is reported and
not changed here, because it alters the package's declared capabilities.

The std pin is the first row that moves the canonical payload or any digest:
none is expected, since payload bytes derive from paxage's own writer.
